# Mark — Telegram News Analyst Bot
## Обзор для команды

Этот документ описывает как устроен бот, какие файлы за что отвечают,
и как работает каждая ключевая функция. Всё написано для тех кто понимает
логику, а не читает каждую строчку кода.

---

## Общая идея

Марк — **однопользовательский** Telegram-бот (отвечает только владельцу).
Он читает Telegram-каналы, складывает посты в PostgreSQL, индексирует их
через AI-векторы, и отвечает на любые вопросы через Google Gemini.

```
Telegram-каналы
      ↓ (Telethon, каждые 15 мин)
  PostgreSQL
      ↓ (фоновые задачи, каждые 10 мин)
  Векторы + Категории
      ↓ (по запросу пользователя)
  Gemini 2.5 Flash → ответ в бот
```

---

## Точка входа: main.py

Всё стартует из `main.py`. Он:
1. Загружает переменные окружения (`utils/env.py`)
2. Создаёт подключение к PostgreSQL (`db/connection.py`)
3. Запускает Telethon-клиент (`parser/telethon_client.py`)
4. Регистрирует все хендлеры (`handlers/`)
5. Запускает APScheduler с фоновыми задачами (`jobs/`)
6. Запускает PTB long polling (бесконечный цикл ожидания сообщений)

Всё это крутится в одном `asyncio` event loop одновременно.

## Блок 1 — Умный поиск по базе

**Кто делал:** поиск + семантика

### Файлы:
- `db/repository.py` — все функции работы с базой
- `handlers/search.py` — хендлер команды `/search`
- `ai/embeddings.py` — векторизация текста через Gemini Embedding API

### Как работает поиск (`repo.search_posts`):

Поиск гибридный — два метода параллельно, потом слияние:

**1. Семантический поиск** (`search_posts_semantic`):
- Вопрос пользователя превращается в вектор через `embed_one()` (Gemini embedding-001)
- В PostgreSQL через расширение pgvector ищутся посты с похожим вектором
- Порог похожести: 0.65 (настраивается в `config.py → SEMANTIC_SIMILARITY_THRESHOLD`)
- Возвращает до `2×limit` постов

**2. Полнотекстовый поиск** (`search_posts_ts`):
- PostgreSQL `plainto_tsquery('russian', ...)` — понимает морфологию (найдёт "санкции" по запросу "санкция")
- Fallback на `ILIKE %...%` если tsquery ничего не дал

**3. RRF-слияние** (Reciprocal Rank Fusion):
- Каждый пост получает score = `1/(60 + rank)` из каждого списка
- Посты которые хорошо ранжированы в обоих списках получают максимальный итоговый score
- Возвращается top-N

### Как работают векторы:

Векторы считаются **фоново**, не в момент запроса.
`jobs/embed_recent.py` каждые 10 минут:
- Берёт до 50 постов без вектора (не старше 2 суток)
- Отправляет их в Gemini Embedding API (`ai/embeddings.py → embed_batch`)
- Сохраняет в колонку `posts.embedding` (формат pgvector)

Вектор = массив из 768 чисел (float32), описывает «смысл» текста.
Чем ближе два вектора → тем похожее тексты по смыслу.

### Ключевые функции:
```
repo.search_posts(query, limit, days)     — гибридный поиск (основной)
repo.search_posts_semantic(vec, ...)      — только семантика
repo.search_posts_ts(query, ...)          — только полнотекст
embed_batch(texts, task_type)             — векторизация пачки текстов
embed_one(text, task_type)                — векторизация одного текста
```

## Блок 2 — Форматы дайджеста

**Кто делал:** дайджесты

### Файлы:
- `ai/digest_service.py` — логика сборки дайджеста
- `ai/prompts.py` — промпт для Gemini (функция `build_digest_prompt`)
- `handlers/digest.py` — хендлер команды `/digest`
- `handlers/menu.py` — обработка кнопок «📅 Дайджест» и «🗂 По категории»
- `jobs/auto_digest.py` — автоматическая отправка по расписанию
- `ai/clustering.py` — кластеризация постов по смыслу

### Виды дайджестов:
- **Ручной** — `/digest` или кнопка «📅 Дайджест» → выбор периода
- **По категории** — кнопка «🗂 По категории» → выбор категории → выбор периода
- **Автоматический** — каждый день в 9:00 и 21:00 (настраивается через `DIGEST_TIME_MORNING` / `DIGEST_TIME_EVENING`)

### Как собирается дайджест (`compose_digest`):

```
1. Достать посты за нужный период из БД (с фильтром по категории если нужно)
2. Разделить на news-посты и expert-посты
3. Кластеризовать news по смыслу (greedy_cluster, порог 0.72)
   → посты об одном событии группируются в кластер
4. Выбрать top-50 news с приоритетом на «горячие сюжеты» (score_posts)
5. Взять expert-посты (до остатка от лимита)
6. Собрать промпт через build_digest_prompt
7. Отправить в Gemini → получить HTML
```

### Структура ответа:
```
🏛 Политика
• Событие 1 — @канал
• Событие 2 — @канал

💸 Экономика
• ...

💬 Мнения экспертов
• @эксперт1: «суть высказывания»
• @эксперт2: «суть высказывания»
```

Категории фиксированы по `config.CATEGORIES` — Gemini не придумывает свои названия.

### Кластеризация (`ai/clustering.py`):
- Берёт embeddings всех news-постов
- Косинусное расстояние < 0.72 → посты об одном событии → один кластер
- `score_posts`: score = `cluster_size + log(text_length)`
- Из каждого кластера в дайджест берётся только 1 пост (самый «тяжёлый»)

### Retry при ошибках Gemini:
Автодайджест повторяет до 4 раз с паузой 5 минут при любой ошибке (503 — перегрузка Google, 429 — квота). Дайджест придёт с опозданием, но придёт.

## Блок 3 — Добавление каналов

**Кто делал:** парсинг каналов

### Файлы:
- `handlers/channels.py` — хендлеры `/add_channel`, `/remove_channel`, `/list_channels`
- `parser/telethon_client.py` — Telethon-клиент (user-account сессия)
- `parser/channel_parser.py` — логика парсинга: `backfill_channel`, `update_channel`
- `parser/scheduler_jobs.py` — обёртка фоновой задачи (`parse_all_channels_job`)
- `db/repository.py` — `upsert_channel`, `remove_channel`, `bulk_insert_posts`

### Типы каналов:
- `news` — новостные каналы. Посты идут в основную часть дайджеста
- `expert` — каналы с мнениями аналитиков. Посты идут в блок «💬 Мнения экспертов»

### Как работает парсинг:

**Первый раз** (новый канал):
- `backfill_channel` — скачивает посты за последние `BACKFILL_DAYS` суток (по умолчанию 1 день)

**Каждые 15 минут** (`parse_all_channels_job`):
- Для каждого канала из БД вызывает `update_channel`
- Telethon итерирует сообщения начиная с последнего сохранённого `tg_message_id`
- Пакеты по 100 постов пишутся в БД через `bulk_insert_posts`
- Вектор и категория при парсинге **не считаются** — это делают отдельные фоновые задачи

### Важно про Telethon:
Бот читает каналы как **обычный пользователь** (не бот-аккаунт).
Для этого нужна `TELETHON_SESSION` — строка сессии, которая генерируется один раз
через `generate_session.py` локально. На Railway она передаётся как переменная окружения.
Файловые сессии не работают (Railway не имеет постоянного файлового хранилища).

## Блок 4 — Настройки Telegram (меню, кнопки, состояния)

**Кто делал:** интерфейс бота

### Файлы:
- `formatters/buttons.py` — все кнопки: главное меню, меню категорий, inline-кнопки под ответами
- `handlers/menu.py` — state-машина: диспетчер текстовых сообщений
- `handlers/start.py` — `/start`, `/help`, `/menu`
- `handlers/callbacks.py` — обработка inline-кнопок (нажатие под ответом)
- `handlers/categories_settings.py` — inline-чекбоксы включения/выключения категорий
- `handlers/common.py` — общие утилиты: `@owner_only`, `safe_send`, `send_long`

### Как устроено главное меню:

`formatters/buttons.py → MENU` — словарь где каждая кнопка = действие:
```python
"📅 Дайджест":   {"kind": "open_digest_period"}   # открыть выбор периода
"🗂 По категории": {"kind": "open_categories"}      # открыть выбор категории
"📌 Глубокий анализ": {"kind": "ask_topic", ...}   # спросить тему
```

`make_main_menu()` собирает `ReplyKeyboardMarkup` — кнопки под полем ввода.

### State-машина (`handlers/menu.py`):

Некоторые действия многошаговые. Текущий шаг хранится в `context.user_data["menu_state"]`:

```
None              → главное меню
"digest_period"   → ждём выбор периода для дайджеста
"categories"      → ждём выбор категории
"period:<cat_id>" → ждём выбор периода для конкретной категории
```

`"awaiting"` в `user_data` — бот ждёт ввод темы для команды (why/map/search).

### Inline-кнопки под ответами:

`topic_actions(context, topic)` — кнопки «📌 Глубже», «🕸 Граф», «📚 Больше деталей».
`digest_actions(context, topics, hours)` — кнопки тем из дайджеста + смена периода.

Темы хранятся в `bot_data` по короткому UUID (callback_data ограничен 64 байтами).
`callbacks.py` обрабатывает нажатия: парсит `"why|<tid>"` → достаёт тему → вызывает нужный хендлер.

### Отправка длинных сообщений:
Telegram режет сообщения на 4096 символов.
`handlers/common.py → send_long` автоматически режет по `\n` и отправляет несколько сообщений.
Inline-кнопки прикрепляются только к **последнему** куску.

## Блок 5 — Графы связей

**Кто делал:** визуализация

### Файлы:
- `handlers/map_graph.py` — хендлер `/map` и кнопки «🕸 Граф»
- `ai/prompts.py` — промпт `build_map_prompt` (инструкция для D2-синтаксиса)
- `formatters/diagram_image.py` — рендер D2 → PNG через kroki.io

### Как работает:
```
1. map_cmd: ищет посты по теме (search_posts)
2. build_map_prompt: промпт с жёсткими правилами D2-синтаксиса
3. Gemini генерирует D2-код (язык описания графов)
4. _extract_d2: вырезает блок ```d2 ... ``` из ответа
5. render_d2_to_png: сжимает D2-код (deflate + base64) → GET-запрос на kroki.io
6. kroki.io возвращает PNG
7. _send_map: отправляет PNG в чат
```

### D2 и цвета узлов:
Каждый узел графа получает один из 4 классов:
- `pos` (зелёный) — поддерживает тему
- `neg` (красный) — против / критикует
- `neu` (серый) — нейтрально упомянут
- `mix` (жёлтый) — противоречивая позиция

Промпт содержит жёсткие правила синтаксиса — без этого kroki.io не рендерит.

### Fallback:
Если kroki.io недоступен — бот отправляет D2-код текстом со ссылкой на `play.d2lang.com`.

## Блок 6 — Глубинный анализ и контекст общения

**Кто делал:** AI-аналитика и память разговора

### Файлы:
- `handlers/why.py` — хендлер `/why тема` и кнопки «📌 Глубже»
- `handlers/free_text.py` — обработка любого свободного текста
- `handlers/chat_history.py` — память разговора (последние 5 пар вопрос-ответ)
- `handlers/context_cmd.py` — `/chronicle тема` (хроника событий)
- `ai/prompts.py` — промпты `build_why_prompt`, `build_free_prompt`, `build_chronicle_prompt`

### Как работает свободный вопрос:

Пользователь пишет что угодно → `menu.py → text_router` → `free_text.py`:

```
1. Поиск постов по вопросу в БД (search_posts)
2. Достать историю разговора (chat_history.get_recent_exchanges)
   → последние 5 пар вопрос-ответ не старше 30 минут
3. build_free_prompt: собрать промпт с персоной Марка + историей + постами
4. Gemini с use_search=True (Google Search grounding — может искать в интернете)
5. add_exchange: сохранить пару в историю
6. Отправить ответ + inline-кнопки «📌 Глубже», «🕸 Граф»
```

### Как работает глубокий анализ (`/why`):

Структура ответа жёстко задана в промпте `build_why_prompt`:
```
📌 Что произошло    — 2-4 предложения с фактами
🔗 Хроника          — ключевые события с датами
🧭 Причины          — почему это произошло
🪞 Исторические параллели — аналоги из прошлого
⚖️ Спор экспертов   — противоположные позиции (если есть)
🤖 Что думаю я (Марк) — личный прогноз
```

Gemini использует Google Search (`use_search=True`) — может ссылаться на живые источники.

### Память разговора (`chat_history.py`):

Хранится в `context.user_data["chat_history"]` — deque на 5 элементов:
```python
{"ts": timestamp, "q": "вопрос пользователя", "a": "выжимка ответа (до 600 символов)"}
```
TTL = 30 минут. Если пользователь молчал дольше — история не подмешивается.

Благодаря этому можно вести диалог:
- «Расскажи про санкции против Ирана»
- «А какова была реакция США?» → Марк понимает что речь всё ещё про Иран

**Важно:** история хранится в памяти процесса (не в БД). При перезапуске бота — сбрасывается.

## Как Gemini получает ответ (`ai/gemini_client.py`)

Все AI-запросы идут через одну функцию `generate(prompt, query_type, use_search)`:

```
1. Проверить кеш в БД (gemini_cache по sha256 промпта)
   → если есть и не истёк TTL → вернуть из кеша
2. Взять активный API-ключ из ротатора (key_rotator.py)
3. Вызвать Gemini 2.5 Flash
   → 429 (квота минутная) → пометить ключ, переключиться на следующий
   → 503 (перегрузка серверов Google) → подождать 10с, повторить до 3 раз
   → все ключи исчерпаны → GeminiQuotaError
4. Сохранить ответ в кеш
5. Вернуть текст
```

### TTL кеша по типу запроса (`config.CACHE_TTL`):
```
digest  → 1 час
free    → 30 минут
search  → 30 минут
why     → 24 часа
map     → 24 часа
```

### Ротация ключей (`ai/key_rotator.py`):
- Несколько ключей → хранятся в кольце
- 429 → ключ на cooldown 60 сек → следующий ключ
- 400/403 → ключ «сломан» → cooldown 24 часа
- Все ключи в cooldown → `GeminiQuotaError` → хендлер показывает подсказку пользователю

## База данных (`db/`)

### Файлы:
- `db/schema.sql` — DDL: все таблицы и индексы
- `db/connection.py` — asyncpg пул соединений + флаг pgvector
- `db/migrations.py` — `apply_schema()`: применяет schema.sql при старте
- `db/repository.py` — все CRUD-функции (единственный слой работы с БД)

### Таблицы:

**posts** — основная:
```
id, channel_id, tg_message_id, text, posted_at, link,
embedding (vector 768d), category (text), fts (tsvector)
```

**channels**:
```
id, username, type (news|expert), title, last_parsed_msg_id
```

**gemini_cache**:
```
prompt_hash, query_type, prompt, response, model, created_at, expires_at
```

**user_category_settings**:
```
user_id, category_id, enabled
```

### pgvector:
Расширение PostgreSQL для хранения и поиска по векторам.
Если pgvector недоступен — семантика отключается, работает только полнотекстовый поиск.
Проверка через `db/connection.is_pgvector_available()`.
